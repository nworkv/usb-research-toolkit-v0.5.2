# Схема «на хосте только Wireshark»

## Принципиальное отличие

На тестируемый Windows-хост не устанавливаются USB Research Toolkit, Python-агент, служба передачи журналов или другой сборщик. Используется только Wireshark с поддержкой USBPcap. Wireshark сохраняет захват USB-трафика непосредственно на SMB-шару Raspberry Pi. Все дополнительные компоненты — Samba, `tshark`, индексатор PCAPNG и фаззер — работают на Raspberry Pi.

Это собирает **USB-трассу**, а не системный журнал Windows. По PCAPNG можно обнаруживать USB-ошибки/сбросы, если они отражены в захвате, но нельзя надёжно доказать BSOD или получить Windows Event Log. Для подтверждения системного сбоя понадобится отдельный внешний сигнал, дамп или журнал, что несовместимо с требованием «на хосте только Wireshark».

## 1. Настроить SMB-шару на Raspberry Pi

Распакуйте проект на Pi, затем в каталоге проекта выполните:

```bash
sudo bash scripts/setup-wireshark-share.sh /srv/usb-captures piuser
```

`piuser` замените на существующего Linux-пользователя. Скрипт устанавливает Samba и `tshark`, создаёт закрытую шару `usb-captures`, включает доступ по паролю и сохраняет резервную копию `smb.conf`. Он разрешает частные IPv4-сети в настройке Samba; дополнительно ограничьте TCP/445 firewall-правилом до IP тестового хоста и держите интерфейс в лабораторной сети. Не публикуйте SMB в Интернет.

Узнайте IP Pi командой `hostname -I`. Например, `192.168.1.20`.

## 2. Открыть шару на Windows

В проводнике Windows введите:

```text
\\192.168.1.20\usb-captures
```

Войдите под Samba-учётной записью, созданной на шаге 1. Это встроенный клиент Windows; устанавливать на тестируемый хост дополнительные программы не требуется.

## 3. Настроить Wireshark на тестовом хосте

1. Откройте Wireshark с правами, необходимыми для захвата USBPcap.
2. Выберите USBPcap-интерфейс, через который подключён тестируемый USB-девайс (обычно интерфейс вида `USBPcapN`).
3. Откройте **Capture → Options**.
4. В поле выходного файла укажите уникальный путь на шаре, например:
   `\\\192.168.1.20\usb-captures\run-20261028-001.pcapng`
5. Запустите захват **до начала** тестовой кампании. Wireshark будет записывать пакеты в PCAPNG по мере захвата.
6. После кампании остановите захват штатной кнопкой Stop. Не используйте один и тот же filename для разных кампаний.

Если требуется обрабатывать трассы по ходу долгой кампании, настройте в Capture Options кольцевой буфер с автоматическим переходом на новый файл по размеру/времени и достаточным числом файлов, чтобы старые трассы не перезаписывались. Индексатор Pi анализирует файл после того, как его размер остаётся неизменным в течение `--stable-seconds`. Для самой надёжной обработки остановите захват в Wireshark после теста.

> Запись по SMB зависит от сетевого соединения. Если хост зависнет или потеряет питание, последний файл может оказаться неполным. Уже переданные байты обычно остаются на Pi, но захват не гарантированно будет корректно закрыт.

## 4. Автоматически индексировать PCAPNG на Raspberry Pi

После настройки SMB-шары запустите в отдельном терминале Pi:

```bash
mkdir -p runs/wireshark-analysis
python3 scripts/pcap-watch.py \
  --watch-dir /srv/usb-captures \
  --out-dir runs/wireshark-analysis \
  --stable-seconds 15
```

Скрипт автоматически замечает новые `.pcapng`/`.pcap`, ждёт стабильного размера, вызывает `tshark` на Pi и создаёт:

- `runs/wireshark-analysis/capture-index.jsonl` — общий индекс всех обработанных трасс;
- `runs/wireshark-analysis/<имя-файла>.analysis.json` — число кадров, временной диапазон, хеш SHA-256, диагностические строки и предупреждения.

Индексатор не удаляет исходные файлы. Для каждой трассы сохраняется хеш, поэтому одинаковое содержимое повторно не анализируется. Чтобы проверить уже стабильные файлы один раз, добавьте `--once`.

## 5. Связать трассу с кампанией

Перед запуском кампании создайте уникальный ID, например `run-20261028-001`, и используйте его и в имени PCAPNG, и в каталоге результатов фаззера. Записывайте seed и время начала/окончания в README/manifest кампании. USB-трасса даёт временные признаки USB-обмена; сама по себе она не устанавливает, что именно профиль вызвал BSOD.

## Что намеренно не используется

- `host-log-agent.py` на тестовом хосте;
- `host-log-receiver.py` для передачи Windows Event Log;
- Python/PowerShell-скрипты или дополнительные службы на тестируемом Windows-хосте.

Старые agent scripts оставлены в репозитории для альтернативных стендов, но для данной схемы они не нужны и не запускаются.


## Очередь дополнительной проверки и повтор случая (v0.4.2)

Runner сохраняет временные метки каждого случая. После завершения кампании он запускает `tshark` на PCAP/PCAPNG из `--capture-dir` и создаёт `review-queue.json`. В очередь попадают случаи, для которых не найден захват/кадры в соответствующем временном окне, `tshark` не смог обработать файл, либо в колонках Protocol/Info обнаружены возможные reset, disconnect, stall, timeout, ошибки или признаки malformed/invalid данных. Это эвристическая очередь для ручного просмотра, а не доказательство сбоя Windows и не гарантированное побайтовое сравнение каждого ответа с JSON-профилем. Часы Raspberry Pi и Windows должны быть синхронизированы; если один PCAPNG охватывает всю кампанию, анализ сопоставляет кадры по времени запуска случая.

Пример кампании (запускайте на изолированном тестовом стенде):

```bash
sudo python3 scripts/usb-gadget-campaign.py \
  --base profiles/templates/hid-mouse.json \
  --count 5 --seed 20261028 --mutations 1 \
  --udc-driver 'fe980000.usb' --udc-device 'fe980000.usb' \
  --dwell-seconds 10 --settle-seconds 3 \
  --capture-dir /srv/usb-captures \
  --out-dir runs/fuzz/hid-smoke \
  --allow-research --confirm-lab
```

По умолчанию кампания продолжает обработку следующих случаев после ошибки отдельного случая. Очередь находится в `runs/fuzz/hid-smoke/review-queue.json`. Каждый профиль остаётся в `case-NNNNN.json`, а SHA-256 сохраняется в журнале.

Повтор выбранного случая после завершения всей кампании (укажи номер из очереди):

```bash
sudo python3 scripts/usb-gadget-campaign.py \
  --base profiles/templates/hid-mouse.json \
  --replay-from runs/fuzz/hid-smoke --replay-case 3 \
  --udc-driver 'fe980000.usb' --udc-device 'fe980000.usb' \
  --dwell-seconds 10 --settle-seconds 0 \
  --capture-dir /srv/usb-captures \
  --out-dir runs/fuzz/recheck-case-00003 \
  --allow-research --confirm-lab
```

Повтор использует сохранённый `case-00003.json`, а не генерирует новую мутацию. Вывод повтора пишется в отдельный каталог. Сохраняйте исходный PCAPNG и не перезаписывайте его, если нужен последующий анализ.


### Рекомендуемый порядок, если Wireshark пишет один общий файл

1. Запустите захват в Wireshark до начала кампании и сохраняйте его в `\\<IP-Raspberry-Pi>\usb-captures`. Если сохраняете файл только после остановки захвата, не закрывайте его с потерей изменений.
2. Запустите кампанию на Raspberry Pi. По умолчанию она продолжает работу после ошибки отдельного профиля; это важно, поскольку отклонение хостом одного варианта ожидаемо.
3. После завершения кампании остановите захват и сохраните итоговый `.pcapng`.
4. На Raspberry Pi повторно проанализируйте захват уже после сохранения файла:

```bash
python3 scripts/review-usb-campaign.py \
  --campaign-dir runs/fuzz/hid-smoke \
  --capture-dir /srv/usb-captures
```

5. Откройте `runs/fuzz/hid-smoke/review-queue.json`. В нём будут номера случаев, причины постановки в очередь и связанные файлы захвата. Для повторного прогона, например случая 3, используйте команду `--replay-from runs/fuzz/hid-smoke --replay-case 3` из предыдущего раздела и задайте новый `--out-dir`.

Сопоставление использует временные метки кадров PCAPNG и запуска случая; синхронизируйте часы Raspberry Pi и Windows. Текстовые признаки Wireshark — эвристика: при подозрительном случае откройте указанные PCAPNG в Wireshark и сравните соответствующие кадры вручную.
